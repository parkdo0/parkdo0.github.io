> **상황** 어느 날 회사 홈페이지에 접속하면 브라우저가 인증서 오류를 띄웠다.
>
> **한 일** 만료된 와일드카드 인증서를 DNS 인증 방식으로 다시 발급받아 웹서버에 적용했다.
>
> **결과** 접속은 바로 돌아왔지만, 자동 갱신까지는 붙이지 못했다.
{: .tldr}

## 상황

개발을 하면서 사내 서버 관리도 같이 맡고 있던 때였다. 하루는 회사 홈페이지에 들어가면 브라우저가 `NET::ERR_CERT_DATE_INVALID`를 띄웠다. 인증서 유효기간이 지난 것이었다.

인증서가 무엇이고 왜 만료되는지는 개념으로는 대충 알고 있었다. 하지만 실제 서버에서 직접 인증서를 다시 받아 본 건 이때가 처음이었다.

## 찾아간 과정

1. **어떤 인증서가 만료됐는지 확인했다.** 서버에는 인증서가 두 개 있었다. 도메인 하나에만 쓰는 단일 인증서와, 하위 도메인 전체에 쓰는 와일드카드 인증서였다. 만료된 건 와일드카드 쪽이었다.
2. **발급 방식이 다르다는 걸 알았다.** 단일 인증서는 웹서버에 확인용 파일을 두는 방식(HTTP 인증)으로 받을 수 있지만, 와일드카드 인증서는 그게 안 된다. 도메인을 내가 가지고 있다는 걸 DNS로 증명해야 했다.
3. **DNS 인증으로 다시 받았다.** certbot을 수동 DNS 인증 모드로 실행하고, 알려 주는 값을 도메인 관리 화면에서 TXT 레코드로 직접 넣었다. 레코드가 반영된 걸 확인한 뒤 진행해서 새 인증서를 받았다.
4. **웹서버에 적용했다.** 새 인증서로 바꾸고 다시 띄우자 접속이 정상으로 돌아왔다.

```bash
# 설명용 예시
sudo certbot certonly --manual --preferred-challenges dns \
  -d "*.example.com" -d "example.com"
```

## 남은 숙제

수동 DNS 인증은 갱신할 때마다 사람이 TXT 레코드를 다시 넣어야 한다. 자동으로 갱신하는 방법도 알아봤지만 끝까지 붙이지는 못했다. 다음 만료 때 같은 일을 또 해야 하는 상태로 남겨 둔 셈이다.

## 돌아보면

| 그때는 | 지금이라면 |
|---|---|
| 인증서가 만료되고 나서야 알았다 | 만료 전에 알림부터 걸어 둘 것 같다 |
| 어느 인증서가 만료됐는지부터 서버에서 찾아봐야 했다 | 서버에 있는 인증서와 만료일, 발급 방식을 미리 정리해 둘 것 같다 |
| TXT 레코드를 손으로 넣고 끝냈다 | DNS 쪽 API를 쓰는 자동 갱신을 먼저 붙여 볼 것 같다 |
{: .compare}

개념으로 아는 것과 실제로 해 보는 건 꽤 달랐다. 와일드카드는 왜 DNS로 받아야 하는지, 수동으로 받은 인증서는 왜 갱신도 손이 가는지 같은 건 직접 해 보고 나서야 감이 왔다.
