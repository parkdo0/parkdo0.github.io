> **상황** 관리자용 업무 플랫폼의 프론트엔드를 혼자 설계하고 구현했다(페이지 148개, 기능 모듈 13개).
>
> **한 일** 확정한 화면 시안을 실제 코드베이스로 옮기면서 폴더 구조, 상태 관리, API 계층, 에러 추적 방식을 정했다.
>
> **결과** 백엔드 없이 mock으로 화면과 흐름을 먼저 완성했지만, 테스트 파일은 0개로 남았다.
{: .tldr}

## 상황

전 직장에서 2025년 12월 26일부터 2026년 2월 21일까지 관리자용 업무 플랫폼의 프론트엔드를 혼자 설계하고 구현했다. React, TypeScript, Vite 기반이었다. 회사 제품이라 코드는 공개하지 않고 구조와 결정만 적는다. 규모는 페이지 148개, 기능 모듈 13개, shadcn/ui 컴포넌트 49개였다.

## 시안은 먼저 확정하고, 구조는 따로

화면은 시안으로 먼저 만들었다. 시안을 여러 번 고쳐 확정했고, 확정된 화면을 실제 코드베이스로 옮겼다. 1월 30일에 관리자 22개 페이지를 포함한 화면을 한꺼번에 이식했고, 2월 10일에는 시안과 동일한지 검증했다.

구조는 따로 잡았다.

1. 12월 29일부터 1월 5일까지 폴더 구조를 네 번 다시 정리했다.
2. 파일 172개를 전수 점검하는 체크리스트를 만들어 1차 점검을 했다.
3. 그 결과로 1월 6일에 API 구조와 코드 컨벤션을 통일했다.

## 그때 정한 것

### 1. 기능 단위 구조

`features/{모듈}/pages, components, api, hooks, types, routes`로 모듈을 업무 경계에 맞췄다. 두 개 이상 모듈이 쓰면 전역으로 올린다는 기준을 문서로 고정했고, features 내부 barrel 파일은 금지, import는 절대경로만 쓰게 했다. 라우트마다 ErrorBoundary, Suspense, lazy 로딩을 붙였다.

### 2. 서버 상태와 클라이언트 상태 분리

- 서버 데이터는 TanStack Query(staleTime 5분, gcTime 30분, 조회 retry 1, 변경 retry 0)
- 클라이언트 상태는 Zustand(인증, 레이아웃)
- Query Key는 `all, lists, list(filters), details, detail(id)` 계층으로 만들어 캐시 무효화 범위를 고를 수 있게 했다.
- API 호출은 axios 인스턴스, 공통 helper, 도메인 api, 도메인 hook의 네 단계로 쌓았다.

### 3. 에러 추적 코드

에러를 출처별 코드(FE, NW, BE, VD)와 8자리 traceId, 시각으로 묶어 토스트에 `BE-500 | a1b2c3d4 | 14:30:25` 형태로 보여줬다. 최근 10건은 localStorage에 남겼다. 사용자가 이 줄만 불러주면 개발자가 로그를 찾을 수 있게 하려는 생각이었다.

### 4. 백엔드 없이 먼저 개발

MSW와 localStorage 기반 mock으로 새로고침해도 CRUD 결과가 유지되게 만들어, 화면과 흐름을 먼저 완성했다. 백엔드가 준비되면 걷어내는 절차(5단계 체크리스트, 엔드포인트 매핑표)도 미리 문서로 남겼다.

## 돌아보면

| 그때는 | 지금이라면 |
|---|---|
| 테스트 파일이 0개였다. Vitest와 Testing Library는 설치만 했다 | 에러 코드 생성처럼 규칙이 분명한 곳부터 테스트를 써 볼 것 같다 |
| MSW 응답과 실제 API의 차이를 검증하는 장치가 없었다 | mock과 실제 응답을 같은 Zod 스키마로 검사해 볼 것 같다 |
{: .compare}

Query Key의 filters 타입은 any로 남아 있었다. 백엔드 연동 일부는 다른 팀원이 맡았다.
