> **상황** MariaDB에서 Oracle로 이관하던 중, 견적 금액을 계산하는 조회 쿼리가 15초 가까이 걸렸다.
>
> **한 일** 빠진 인덱스를 추가했지만 옵티마이저가 쓰지 않아서, 힌트로 인덱스를 강제했다.
>
> **결과** 응답이 15초에서 약 1초로 줄었다.
{: .tldr}

## 상황

견적 관련 시스템의 DB를 MariaDB에서 Oracle로 옮기는 프로젝트였다. 나는 저연차였고, 이전 개발사가 중간에 손을 뗀 프로젝트를 이어받은 상태라 납기가 빠듯했다. 롤백 계획은 따로 없다고 전달받았다.

이관 테스트를 하던 중, 견적 금액을 계산하는 조회 쿼리 하나가 응답에 **15초** 가까이 걸렸다. 견적 마스터, 견적 상세, 견적 상태, 자재 테이블을 조인하고 서브쿼리가 붙은 쿼리였다. MariaDB에서는 문제없던 쿼리였다.

## 그때 한 일

1. **실행계획 확인.** 실행계획을 떠 보니 Full Table Scan이 나오고 있었다.
2. **인덱스 확인.** 이관 과정에서 빠진 인덱스가 있어서 추가했다.
3. **그런데 그대로였다.** 인덱스를 만들었는데도 옵티마이저가 그 인덱스를 쓰지 않았다.
4. **힌트로 고정.** 결국 `/*+ INDEX(...) */` 힌트로 인덱스를 쓰도록 강제했고, 응답이 약 1초로 줄었다.

```sql
SELECT /*+ INDEX(em 인덱스명) */
       ...
  FROM 견적마스터 em
  JOIN 견적상세 ed ON ...
 WHERE ...
```

최종 검증은 당시 개발팀장님이 같이 봐 주셨다.

> 오래된 일이라 인덱스 컬럼 구성 같은 세부 내용은 정확히 기억나지 않는다. 아래 내용은 그때 확인한 사실이 아니라, 나중에 공부하면서 다시 본 것이다.
{: .note}

## 나중에 공부하며 다시 본 것

당시에는 "인덱스를 만들었는데 왜 안 타지?"에서 힌트로 바로 넘어갔다. 나중에 공부하면서 순서를 다르게 봤어야 했다는 생각이 들었다.

### 통계 정보

Oracle 옵티마이저는 테이블 통계(건수, 값 분포 등)를 보고 실행계획을 고른다. 데이터를 대량으로 옮긴 직후에는 통계가 비어 있거나 실제와 많이 다를 수 있고, 그러면 인덱스가 있어도 Full Scan이 더 싸다고 잘못 판단할 수 있다. 이관 직후라는 상황을 생각하면, 힌트보다 통계 수집을 먼저 해 봤어야 했다.

```sql
BEGIN
  DBMS_STATS.GATHER_TABLE_STATS(ownname => '스키마명', tabname => '견적마스터', cascade => TRUE);
END;
/
```

(`ANALYZE TABLE ... COMPUTE STATISTICS`는 옛 방식이라 지금은 `DBMS_STATS`를 쓴다.)

### 힌트

힌트는 지금 데이터 기준으로는 빠르지만, 데이터 분포가 바뀌어도 같은 경로를 강제한다. 인덱스 이름이 바뀌면 힌트는 조용히 무시된다.

### 서브쿼리 구조

SELECT 절이나 WHERE 절의 상관 서브쿼리는 바깥 행마다 반복 실행될 수 있다. 조인이나 미리 집계한 결과와의 조인으로 바꿀 수 있는지도 볼 만한 부분이었다.

## 돌아보면

| 그때는 | 지금이라면 |
|---|---|
| 인덱스를 만들어도 안 타서 힌트로 고정했다 | 통계 정보부터 다시 모아 볼 것 같다 |
| 힌트를 넣고 거기서 끝냈다 | 왜 넣었는지 주석으로 남기고, 통계를 정상화한 뒤 힌트 없이도 같은 계획이 나오는지 확인해 볼 것 같다 |
| 인덱스와 힌트 쪽만 봤다 | 상관 서브쿼리를 조인으로 바꿀 수 있는지도 같이 볼 것 같다 |
| 응답 시간(15초 → 약 1초)만 남았다 | 실행계획 전후, 읽은 블록 수 같은 값도 같이 남겨 둘 것 같다 |
{: .compare}

이관 직후 느려진 쿼리에서 나는 인덱스 누락만 봤고, 인덱스를 만들었는데도 안 탈 때 "옵티마이저가 왜 그렇게 판단했나"를 묻지 않았다. 전후 기록을 남겨 뒀다면 이 글도 더 정확하게 쓸 수 있었을 것 같다. 결과 숫자보다 과정과 근거가 나중에 더 쓸모 있었다.
