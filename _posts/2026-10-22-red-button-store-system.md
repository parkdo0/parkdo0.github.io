>
> **한 일** 세 종류 사용자를 URL 경로와 JWT role로 나눈 Next.js 앱 하나에 인증, 주문 트랜잭션, SSE 채팅을 넣었다.

> **결과** 2026년 2월 8일부터 24일까지 커밋 20개를 쌓았고, 연결마다 1.5초씩 DB를 조회하는 채팅 구조와 테스트 부재가 숙제로 남았다.
{: .tldr}

## 무엇을 만들었나

어느 보드게임 카페 프랜차이즈의 매장 운영 시스템을 클론하고 고도화한 개인 프로젝트였다. 2026년 2월 8일 Create Next App으로 시작해 2월 24일까지 커밋 20개를 쌓았다.

| 사용자 | 진입 경로 | 인증 방식 |
| --- | --- | --- |
| 고객 태블릿 | `/` | 매장 선택 + PIN + 테이블 번호 |
| 매장 관리자 | `/admin/store` | 아이디/비밀번호 |
| 본사 관리자 | `/admin/hq` | 아이디/비밀번호 |

스택은 Next.js 16(App Router), TypeScript, Tailwind CSS 4, Prisma 5, MySQL 8, jose(JWT), bcryptjs였다. README에는 아키텍처, 인증, 주문, 채팅 흐름과 DB 스키마를 SVG 다이어그램으로 그려 두었다.

## 하나의 앱, 세 역할

세 사용자를 별도 앱으로 나누지 않고 URL 경로와 JWT 세션의 role 값으로 구분했다. Middleware가 모든 요청에서 JWT를 검증하고, 경로마다 들어올 수 있는 역할을 정했다.

- `/admin/hq`: 본사 관리자만
- `/admin/store`: 매장·본사 관리자만
- 고객 화면: 테이블 세션과 본사 관리자만

데이터는 두 갈래로 흘렀다. 화면 조회는 Server Component가 Prisma로 바로 읽고, 주문 생성이나 채팅 전송처럼 사용자 동작이 있는 곳만 API Route를 거치게 했다.

## 인증

관리자는 bcrypt로 비밀번호를 확인한 뒤 JWT를 만들어 쿠키에 넣었다. 만료는 영업시간을 기준으로 **16시간**으로 잡았다.

태블릿은 매장을 열 때 직원이 한 번 설정하는 방식이었다. 매장 코드로 테이블을 찾고, `{ role: "TABLE", storeId, tableNo, tableId }`를 담은 JWT를 발급했다.

NextAuth 대신 jose를 고른 이유는 두 가지였다. Middleware가 도는 Edge Runtime과 호환되고, 매장 코드 기반 로그인이 OAuth 중심 구조와 맞지 않았기 때문이다.

## 주문과 실시간 채팅

주문 생성은 `prisma.$transaction` 하나로 묶었다.

1. 주문을 만든다
2. 메뉴와 옵션을 조회해 가격을 계산한다
3. 주문 항목에 메뉴명과 가격을 복사해 저장한다
4. 총액을 갱신한다

중간에 하나라도 실패하면 전부 롤백된다. 이름과 가격을 복사해 두니 나중에 메뉴 가격을 바꿔도 지난 주문 금액은 변하지 않았다. 매장과 테이블은 요청 값이 아니라 쿠키 세션에서만 꺼냈다.

```ts
// 세션에서 storeId/tableId 추출 (클라이언트 값 무시)
const storeId = session.storeId!;
const tableId = session.tableId!;
```

채팅은 전송을 `POST /api/chat`, 수신을 `GET /api/chat/stream`으로 나눴다. WebSocket 대신 **SSE**를 고른 이유는 수신만 스트리밍하면 충분했고, Route Handler만으로 만들 수 있었고, EventSource가 재연결을 알아서 해 주기 때문이었다.

서버는 스트림 안에서 1.5초마다 새 메시지를 조회해 보내고 30초마다 heartbeat를 보냈다. 고객 화면은 보낸 메시지를 먼저 그린 뒤 실제 ID로 바꾸고, 받은 ID 집합으로 중복을 걸렀다. 관리자는 테이블 번호 없이 연결해 전체 테이블 메시지와 미읽음 수를 받았다.

## 돌아보면

| 그때는 | 지금이라면 |
|---|---|
| 연결마다 1.5초 간격으로 DB를 조회했다 | 메시지 저장 시점에 이벤트를 발행하는 방식을 검토해 볼 것 같다 |
| 테스트 파일 없이 만들었다 | 주문 금액 계산부터 테스트를 붙여 볼 것 같다 |
| README와 실제 코드가 어긋난 채로 두었다 | 코드가 바뀔 때 README 숫자와 표기도 같이 맞춰 둘 것 같다 |
{: .compare}

연결마다 DB를 조회하니 태블릿이 늘면 쿼리도 그만큼 늘어나는 구조였다. 그 밖에 남은 부분도 있었다.

- 결제는 단말기 연동 없이 주문 생성 때 바로 완료로 저장하는 mock이었다.
- README의 모델 수(23개)와 스키마(24개), 주문 상태 변경 메서드 표기(POST, 실제는 PATCH)가 어긋나 있었다.
