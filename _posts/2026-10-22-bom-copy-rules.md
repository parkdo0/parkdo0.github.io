> **상황** 견적 시스템의 사양 복사 기능이 원본 청구의 특성을 통째로 복사하고 있었다.
>
> **한 일** 사용자가 고른 교체 품목의 특성만 복사하도록, 특성 유형과 그룹 방향, N:1 제한 같은 규칙을 표로 정리하고 구현했다.
>
> **결과** 그룹 판정 버그를 계층 깊이 조건으로 고쳐 개발 서버에 배포했고, 제약 조건은 인수인계 문서에 따로 적었다.
{: .tldr}

## 상황

2024년 말, 견적 시스템에서 "사양 복사" 기능을 고쳤다. 기존 기능은 원본 청구의 특성을 통째로 복사했는데, 교체 청구에서는 **사용자가 고른 교체 품목의 특성만** 복사해야 했다.

말로는 한 줄이지만, 실제로는 규칙이 여러 겹이었다.

## 정리한 규칙

구현 전에 정리한 규칙이다.

| 조건 | 복사 |
|---|---|
| 특성 유형 1, X | 복사 불가 |
| 특성 유형 5 | 항상 복사 가능 |
| 특성 유형 2, 3 | 대상 쪽에 같은 특성이 없으면 불가 |
| 이름에 "적용수량"이 들어간 특성 | 불가 |
| 특성값 그룹 | 원본이 부모, 대상이 자식인 방향일 때만 가능 (3단계 계층) |
| 여러 건을 한 건으로 복사(N:1) | 교체 청구일 때만, 최대 20건, 같은 계약 안에서만 |

복사할 수 없는 항목은 화면에서 체크박스를 비활성화해서 처음부터 고를 수 없게 했다.

## 구현하면서 정한 것

- **판정은 서버에서, 화면은 결과만.** 이 청구가 교체 대상인지는 서버에서 판정하고, 화면에는 "복사 가능 여부"만 내려주게 했다. 화면에서 같은 규칙을 다시 계산하면 규칙이 두 군데로 갈라진다고 봤다.
- **검증은 끝까지 하고 나서 반환.** 처음 구현에서는 유형 5 특성이 하나라도 있으면 그 자리에서 바로 "가능"을 반환했다. 그러면 뒤에 있는 다른 특성 검사를 건너뛰게 된다. 모든 검사를 끝낸 뒤에 결과를 반환하도록 순서를 바꿨다.
- **있는 함수 재사용.** 그룹 관계를 확인하는 기존 함수가 있어서 새로 만들지 않고 그대로 썼다.

### 그룹이 같다고 잘못 나오던 버그

테스트 중에 특성값이 서로 다른데 같은 그룹으로 판정되는 경우가 나왔다. 그룹 정보를 행마다 조인하는 과정에서 계층 깊이를 구분하지 않은 것이 원인이었다. 그룹 데이터를 `WITH` 절로 먼저 뽑아 두고, 계층 깊이 컬럼을 조건에 넣어 해결했다.

```sql
-- 설명용 예시
WITH grp AS (
  SELECT 특성값코드, 그룹코드, 그룹깊이
    FROM 특성값그룹
)
SELECT ...
  FROM 청구특성 c
  JOIN grp g ON g.특성값코드 = c.특성값코드
            AND g.그룹깊이 = :깊이
```

## 마무리와 인수인계

개발 서버에 배포하고, 통합 테스트는 다른 기능 테스트와 함께 진행하기로 일정을 잡았다. 인수인계 문서에는 화면 변경뿐 아니라 쿼리 수정 내용과 20건 제한, 같은 계약 조건 같은 제약을 따로 적었다. 이런 제약은 코드만 봐서는 왜 있는지 알기 어렵다고 생각했다.

## 돌아보면

| 그때는 | 지금이라면 |
|---|---|
| 처음에는 유형 5 특성이 있으면 그 자리에서 바로 "가능"을 반환했다 | 모든 검사를 끝낸 뒤 반환하는 순서를 처음부터 정해 두고 시작할 것 같다 |
| 규칙 표를 테스트 케이스로 바꿔 두지 않았다 | 표의 각 줄을 테스트 하나로 옮겨 둘 것 같다 |
{: .compare}

규칙 표는 이미 줄마다 조건과 결과가 나뉘어 있어서, 그대로 테스트 하나씩이 될 수 있었다.
