> **문제** 외주 과업지시서 첨부를 추가했는데, DB에 91,202번으로 저장된 첨부 대신 ERP에는 91,200번 파일이 전송됐다.
>
> **원인** ERP로 보낼 값을 만드는 조회 쿼리가 새 첨부 ID가 아니라 기존 1번 슬롯 값을 보내고 있었다.
>
> **결과** 전송 쿼리 분기에 4번째 슬롯으로 새 첨부 ID를 추가해서 해결했다.
{: .tldr}

## 만든 기능

2025년 가을, 프로젝트 관리 시스템의 구매 요청 화면에 **외주 과업지시서 첨부** 기능을 추가했다.

- 구매 견적 상세 테이블에 첨부 파일 ID 컬럼 추가 (기존 데이터를 위해 NULL 허용)
- 외주비 금액이 있는데 첨부가 없으면 저장 전에 경고 확인창 표시
- 과업지시서 양식 내려받기 버튼
- 업로드는 이미 있던 공통 파일 업로드 기능을 그대로 사용
- 첨부 정보는 외부 ERP로 연동 전송. ERP 쪽 수신 개발은 해당 담당자에게 필요한 필드를 전달

## 문제

테스트하는데 ERP에 다른 파일이 들어가 있었다. 우리 DB에는 첨부 ID가 91,202로 저장됐는데, ERP에는 91,200번 파일이 전송된 상태였다.

## 찾아간 과정

1. 저장은 맞게 됐는지 봤다. DB 값은 91,202로 정상이었다.
2. 전송 데이터는 어디서 만드는지 봤다. ERP로 보내는 값을 만드는 조회 쿼리를 확인했다.
3. 원인이 거기 있었다. 그 쿼리가 기존 첨부 슬롯 중 **1번 슬롯**(원가 자료 등 기존 첨부용) 값을 보내고 있었고, 새 과업지시서 ID는 전송 대상에 들어가 있지 않았다.

기존 1~3번 슬롯은 각각 다른 용도로 이미 쓰이고 있어서 덮어쓸 수 없었다. 그래서 전송 쿼리의 분기에 **4번째 슬롯**으로 새 첨부 ID를 추가해서 해결했다.

## 고민했던 것: 트랜잭션

파일 업로드와 구매 요청 저장은 서로 다른 요청이라, 하나의 트랜잭션으로 묶이지 않았다. 업로드는 됐는데 저장이 실패하면 파일만 남는다.

당시에는 저장이 실패하면 화면에서 방금 올린 파일을 삭제 요청하는 방식으로 처리했다. 공통 업로드 기능을 고치지 않는 범위에서 고른 방법이었다.

## 돌아보면

| 그때는 | 지금이라면 |
|---|---|
| 저장이 실패하면 화면에서 방금 올린 파일을 삭제 요청했다 | 저장과 연결되지 않은 파일을 주기적으로 정리하는 배치나, 임시 업로드 후 저장 시점에 확정하는 구조를 검토해 볼 것 같다 |
| "이건 트랜잭션으로 묶여야 하지 않나?"를 정확히 판단하지 못했다 | 트랜잭션 경계부터 다시 짚고 들어갈 것 같다 |
| ERP 연동 호출을 주석 처리하고 로컬에서 화면으로 확인하는 정도로 테스트했다 | 외부 연동 부분을 가짜로 바꿔 끼울 수 있게 만들어 검증해 볼 것 같다 |
{: .compare}

화면에서 지우는 방식은 삭제 요청까지 실패하면 결국 파일이 남는다. 이 기능을 하면서 트랜잭션 개념이 흔들렸고, 트랜잭션 경계는 제대로 다시 공부해야 할 부분으로 남았다.
