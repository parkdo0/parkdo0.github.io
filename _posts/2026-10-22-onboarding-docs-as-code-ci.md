## 상황

팀에 새로 오는 개발자를 위한 온보딩 문서를 만들었다. 대상은 경력 3년 이상이지만 이 회사 도메인은 처음이고 사수가 없는 사람이었다. 판단 기준은 하나로 정했다. **"이 문서만 보고 혼자 일할 수 있는가."**

구성은 1~7부와 용어사전, PDF 8개였다.

- 도메인 개념
- 팀 규칙과 첫날
- 개발계 ERP 실습
- 개발환경과 레포 구조
- 도메인과 테이블·프로시저·코드의 연결
- 유지보수 한 건 사례
- 배포 예외

PDF는 직접 편집하지 않고 코드처럼 다뤘다.

1. HTML 원본과 생성 스크립트(`*_gen.py`)가 쪽을 만든다.
2. `build.py`가 쪽을 조립한다.
3. Playwright가 PDF로 렌더한다.

쪽 크기(1280×720), 색, 제목 스타일은 고정했고, 본문 하단은 655px 안에 들어가게 했다.

## AI 작업 규칙 파일

팀원 누구든 이 레포를 AI 코딩 도구로 열어 문서를 고치더라도 같은 규칙을 따르게 하고 싶었다. 레포 루트의 규칙 파일에 적은 것 중 핵심은 이랬다.

- 사람 이름을 쓰지 않고, 캡처 속 개인정보는 블러 처리
- 사실은 확인한 것만 쓰고, 확인하지 못한 것은 본문이 아니라 PR 본문에 [확인 필요]로
- 같은 내용은 한 곳에만 쓰고, 나머지는 쪽 제목으로 가리키기
- 넘치면 글자를 줄이지 말고 행이나 쪽을 나누기
- 생성물은 직접 고치지 않고 원천 파일만 수정
- 수정 후 전체 빌드, 넘침 검사, 바뀐 쪽 이미지 직접 보기, 이전 Release와 쪽별 비교를 순서대로

넘침 검사 스크립트가 절대 위치 박스와의 겹침은 못 잡는다는 한계도 규칙에 적어 두고, 렌더 이미지를 눈으로 확인하게 했다. PR 템플릿에는 바뀐 부·쪽, 이유, 근거(화면·코드 경로·SQL)를 적는 표와 검증 체크리스트를 넣었다.

## CI가 막는 것

GitHub Actions가 PR마다 같은 검사를 돌리게 했다.

1. 문서 원본을 고쳤는데 개정 이력(`revisions.py`)에 새 버전 항목이 없으면 실패
2. 버전 규칙과 개정 이력 형식 검사. 버전을 건너뛰거나 낮추면 실패
3. 8개 부 전체 넘침 검사
4. PDF 렌더 후 최신 Release PDF와 쪽별 픽셀 비교, 결과는 job summary에
5. merge하면 올라갈 Release 제목과 패치노트 미리보기, PDF artifact 업로드

main에 merge되면 새 버전 항목이 있을 때만 Release와 패치노트를 만들고, 같은 태그가 이미 있으면 실패하게 했다. 각 PDF 마지막 쪽에는 부별 개정 이력이 자동으로 들어갔다.

픽셀 비교를 쓰려면 같은 입력이 같은 그림을 내야 했다. 그래서 실행 이미지를 ubuntu-24.04로 고정하고, 폰트 설치를 워크플로에 명시했다. 첫날에는 Medium 굵기 폰트가 빠지고 Release 자산의 한글 파일명이 깨졌다. 그래서 자산 이름은 영문으로 두고, 표시 이름과 zip 안 파일명만 한글로 나눴다.

## 실제로 돌아간 것

1. 2026-10-19에 v0.1을 냈다.
2. 10-20 v0.2에서 한 앱의 백엔드 서술을 정정했다. 운영 API 주소를 확인해 보니 문서와 다른 백엔드를 부르는 곳이 있었다.
3. 10-22 v0.3에는 1차 피드백 3건(용어 뜻 풀이, 설치 프로그램 링크, 계정 메일을 못 받았을 때의 담당자)을 반영했다.

버전 표기는 처음에 v1.0, v1.1로 달았다가, 0.x를 초안·피드백 기간으로 쓰는 규칙으로 바꿨다. 10-22 기준 PR은 10개였다.
