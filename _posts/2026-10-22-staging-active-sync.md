> **문제** 관리자가 고친 단가가 검증 전에 곧바로 영업 담당자의 견적 화면에 반영되는 구조였다.
>
> **한 일** 기준 테이블 10여 개를 스테이징과 두 벌로 나누고, 뷰 전환과 백업·롤백이 있는 동기화를 만들었다.
>
> **결과** 관리자는 스테이징에서 고치고 사용자는 운영 쪽을 보게 됐고, 단가 데이터 약 15만 건을 개발 DB에서 운영 DB로 옮겼다.
{: .tldr}

## 문제

견적 시스템의 단가·원가 기준 데이터를 다루는 일이었다(2024년). 관리자가 단가를 수정하면 그 값이 곧바로 영업 담당자의 견적 화면에 반영되는 구조였다. 검증이 끝나지 않은 단가가 견적에 나갈 수 있다는 뜻이었다.

## 바꾼 방식

### 1. 같은 구조의 테이블을 두 벌로

견적에 쓰이는 기준 테이블 10여 개에 대해, 같은 구조의 스테이징 테이블(`_STAGING`)을 만들었다. 관리자는 스테이징에서 수정하고, 사용자는 운영 쪽 데이터를 보게 했다.

### 2. 사용자용 뷰와 관리자용 뷰

화면 쿼리가 테이블을 직접 보지 않고 뷰를 보게 했다. 어느 세트가 현재 운영인지는 이력 테이블의 최신 플래그로 정하고, 뷰가 그 값을 보고 A/B 중 한쪽을 보여주도록 했다. 누가 언제 바꿨는지 이력 테이블에 남도록 한 것도 이 때문이었다.

솔직히 이 방식에 이르기까지 **4주쯤** 헤맸다. 파라미터를 받는 뷰, 세션 값을 읽는 함수, 프로시저를 차례로 시도하다가, 이력 테이블과 `UNION ALL` 뷰로 정리됐다.

### 3. 되돌릴 수 없는 동기화에는 두 번 확인

스테이징을 운영으로(또는 반대로) 맞추는 동기화를 버튼 하나로 만들었다. 한번 실행하면 되돌리기 어려운 작업이라, 확인을 두 번 받고 정해진 문구를 직접 입력해야 실행되게 했다.

동기화 프로시저는 이렇게 동작했다.

1. 대상 테이블을 FK 없는 백업 테이블에 먼저 복사
2. 자식 테이블부터 FK 순서대로 삭제 후 다시 입력
3. 서비스 계층에서 하나의 트랜잭션으로 묶고, 중간에 실패하면 전체 롤백

## 개발 데이터를 운영으로 옮길 때

단가 데이터 약 15만 건을 개발 DB에서 운영 DB로 옮기는 작업도 했다.

1. DB Link로 개발 데이터를 읽어 옴
2. 교체 전에 운영 데이터를 이력 테이블에 백업
3. 옮긴 뒤 건수 비교로 검증
4. 문제가 생기면 버전명 기준으로 되돌리는 롤백 프로시저 준비
5. 프로시저는 협의를 거쳐 DB 툴에서 직접 실행

## 돌아보면

| 그때는 | 지금이라면 |
|---|---|
| 테이블을 통째로 지우고 다시 넣는 방식으로 동기화했다 | 그동안의 잠금, 그 사이 사용자가 조회하면 어떻게 되는지, 데이터가 커지면 걸리는 시간부터 따져 볼 것 같다 |
| 백업을 언제 지울지는 "나중에"로 남겨 뒀다 | 백업을 만들 때 정리 규칙도 같이 정해 둘 것 같다 |
| 시노님(synonym)을 바꿔 끼우는 방식처럼 더 단순한 전환 방법과 비교해 보지 않았다 | 이원화를 정하기 전에 그런 대안부터 나란히 놓고 비교해 볼 것 같다 |
| 동기화 결과 검증이 건수 비교와 화면 확인뿐이었다 | 동기화 결과를 확인하는 자동 테스트를 붙여 볼 것 같다 |
{: .compare}

운영 데이터를 바꾸는 기능은 "어떻게 바꾸나"보다 "잘못 바꿨을 때 어떻게 되돌리나"를 먼저 정해야 한다는 것을, 이 일을 하면서 배웠다.
